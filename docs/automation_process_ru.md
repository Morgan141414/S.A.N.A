# Автоматизация разработки S.A.N.A.

Этот документ описывает, как разработка S.A.N.A. ведется в режиме маленькой команды: Architect, Developer, QA, Safety Reviewer и Product/Clinical Reviewer.

## Цель

Довести текущую версию S.A.N.A. до 100% готовности v0.1, а затем использовать тот же процесс для следующих версий ТЗ.

100% готовности означает не абсолютную идеальность продукта, а выполнение всех критериев готовности конкретной версии: код, тесты, документация, safety-проверки, API-контракт и список известных ограничений.

## Рабочий цикл

1. Architect определяет границы версии и архитектурные изменения.
2. Developer реализует изменение в коде.
3. QA добавляет или расширяет тесты.
4. Safety Reviewer проверяет риски вредных ответов, кризисные сценарии и медицинские границы.
5. Product/Clinical Reviewer сверяет поведение с ТЗ и тоном S.A.N.A.
6. Quality gate запускается перед коммитом.
7. Документация обновляется вместе с поведением.

## Команды

Полный локальный цикл:

```bash
make dev-cycle
```

Только обязательные проверки:

```bash
make check
```

Отчет по качеству:

```bash
make quality-report
```

## Правила работы с субагентами

- Explorer-агенты используются для аудита, поиска gaps и независимого ревью.
- Worker-агенты используются для ограниченных задач с четкой зоной ответственности.
- Несколько worker-агентов не должны редактировать одни и те же файлы одновременно.
- Финальная интеграция остается за основным разработчиком.
- Любой вывод субагента проверяется через quality gate.

## Минимальный quality gate

```text
ruff check
pytest
docs consistency tests
API contract tests
risk classifier tests
safety checker tests
policy router tests
```

## Переход к следующему ТЗ

Новая версия ТЗ начинается только после того, как:

- v0.1 readiness checklist закрыт;
- quality gate проходит;
- известные ограничения записаны;
- следующий backlog сформирован;
- рискованные решения вынесены в отдельные задачи.
