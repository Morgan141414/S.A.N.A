# Release readiness S.A.N.A. v0.1

Статус: черновой release readiness/status документ.

Дата среза: 2026-06-01.

Этот документ фиксирует состояние v0.1 как safety-first прототипа. Он не заменяет `docs/v0_1_readiness_ru.md`, а дает релизный срез: что уже собрано, что блокирует 100% готовности, какие P0/P1/P2 остаются и какие проверки должны проходить перед выпуском.

## Цель v0.1

v0.1 должна подтвердить минимальный безопасный поток:

```text
User message
  -> Input normalization
  -> Risk classifier
  -> Conversation policy router
  -> support_response
  -> Safety checker
  -> Final answer
```

Версия v0.1 не является медицинским продуктом, не ставит диагнозы, не назначает лекарства, не заменяет психолога, психиатра, врача, кризисную линию или экстренные службы.

## Текущий статус

Общий статус: условно готово к внутреннему release candidate после прохождения quality gate и отдельного QA/Safety review.

Что выглядит готовым по текущей структуре проекта:

- есть FastAPI backend и endpoint chat pipeline;
- зафиксирован базовый response contract: `risk_level`, `risk_score`, `conversation_mode`, `risk_assessment`, `safety_check`, `response`;
- есть deterministic risk classifier для уровней `low`, `medium`, `high`, `emergency`;
- есть правило immediate danger override для `emergency`;
- есть policy router для режимов `support`, `deep_support`, `minor_support`, `crisis`, `emergency`;
- есть генерация поддерживающих ответов для базовых режимов;
- есть safety checker для окончательных диагнозов, medication advice и слабой кризисной реакции;
- есть тесты API-контракта, risk classifier, policy router, chat pipeline, response safety и docs consistency;
- есть quality gate через `make check`, а также `make dev-cycle` и `make quality-report`;
- основные документы проекта уже описывают ТЗ, архитектуру, clinical behavior, процесс разработки и automation process.

Что пока считать не финально подтвержденным:

- прохождение полного `make check` на текущем рабочем дереве;
- результаты ручного QA по реальным пользовательским сценариям;
- Safety Reviewer sign-off для `high` и `emergency` сценариев;
- Product/Clinical Reviewer sign-off по тону, клинической осторожности и возрастной уместности;
- полный список известных ограничений в финальном release note;
- отсутствие чужих незавершенных изменений в рабочем дереве перед релизом.

## Что блокирует 100%

До статуса "v0.1 готова на 100%" должны быть закрыты следующие блокеры:

- полный quality gate проходит без исключений: `make check`;
- для релизного среза сохранен результат `make quality-report` или эквивалентный отчет;
- QA подтвердил end-to-end сценарий chat endpoint для `low`, `medium`, `high`, `emergency`;
- Safety Reviewer подтвердил, что кризисные и emergency-ответы не ослабляют безопасность;
- Product/Clinical Reviewer подтвердил, что ответы не звучат как диагноз, лечение или замена специалиста;
- все P0 ниже закрыты или явно перенесены решением Architect + Safety Reviewer;
- известные ограничения v0.1 записаны в release result перед передачей наружу;
- нет открытых P0-дефектов.

## P0 к закрытию

P0 - обязательный минимум для релиза v0.1.

- Запустить и зафиксировать результат `make check`.
- Запустить и зафиксировать результат `make quality-report` или `make dev-cycle`.
- Проверить chat endpoint вручную или автотестом на четырех уровнях риска: `low`, `medium`, `high`, `emergency`.
- Подтвердить, что `high` всегда идет в `crisis`, а `emergency` - в `emergency`.
- Подтвердить, что immediate danger признаки: план, средство, срок, текущий вред себе или другим - переводят риск в `emergency`.
- Подтвердить, что safety checker исправляет или блокирует окончательный диагноз, medication advice и слабую кризисную реакцию.
- Проверить, что `response` равен `safety_check.safe_response` в API-ответе.
- Проверить, что невалидный вход в chat endpoint отклоняется корректно.
- Провести Safety Review для кризисных сценариев и сценариев несовершеннолетних.
- Зафиксировать known limitations v0.1: нет клинической валидации как medical device, нет production локализации ресурсов помощи, нет полноценного хранения сессий и нет LLM/RAG контура.

## P1 к закрытию после RC

P1 - важные задачи, которые усиливают качество, но не должны блокировать внутренний RC при явных ограничениях.

- Расширить ручную QA-матрицу: тревога, паника, выгорание, горе, вина, одиночество, конфликт, подозрение на депрессивное состояние.
- Добавить больше age-aware сценариев для детей, подростков, взрослых и пожилых пользователей.
- Уточнить формат release report: версии, команды проверок, результаты, known limitations, reviewer approvals.
- Расширить негативные тесты на опасные советы, давление, обесценивание, обещание гарантированной безопасности и скрытие опасности.
- Подготовить шаблоны QA/Safety/Product review для повторяемого релизного процесса.
- Уточнить многоязычные ожидания: когда отвечать на языке пользователя и какие языки реально поддержаны в v0.1.
- Добавить больше проверок на соответствие документации фактическому API и режимам.

## P2 после v0.1

P2 - задачи для последующих версий.

- Подключить LLM-генерацию только за deterministic safety-контуром.
- Добавить хранение сессий после согласования privacy и safety требований.
- Подготовить `resource_recommender` с локализованными и проверенными ресурсами помощи.
- Добавить RAG/Qdrant только на vetted support materials.
- Создать датасет безопасных и небезопасных диалогов для оценки и будущего обучения.
- Подготовить preference evaluation и расширенную метрику качества ответа.
- Проработать LoRA/QLoRA только после экспертного и clinical review.

## Обязательные проверки

Перед релизом должны проходить:

```bash
make check
```

Эта команда должна покрывать:

- Ruff/static checks для backend;
- pytest;
- API contract tests;
- risk classifier tests;
- policy router tests;
- chat pipeline tests;
- response safety tests;
- docs consistency tests.

Желательно перед финальным release decision также выполнить:

```bash
make quality-report
```

или полный цикл:

```bash
make dev-cycle
```

Если какая-либо проверка не запускалась, release result должен явно содержать:

- название проверки;
- причину пропуска;
- остаточный риск;
- ответственную роль за решение: Developer, QA, Safety Reviewer, Product/Clinical Reviewer или Architect.

## Минимальная ручная QA-матрица

До 100% готовности нужно вручную подтвердить минимум следующие сценарии:

- `low`: грусть, усталость, одиночество без признаков непосредственной опасности;
- `medium`: устойчивое ухудшение состояния, тревога, безнадежность или нарушение сна;
- `high`: мысли о смерти, самоповреждении, насилии или потере контроля без конкретного немедленного плана;
- `emergency`: план, средство, срок, текущий вред себе или другим;
- minor scenario: несовершеннолетний пользователь с небезопасной ситуацией или страхом рассказать взрослым;
- unsafe response scenario: попытка получить диагноз, назначение лекарства или совет скрыть опасность.

Ожидаемый результат:

- `low` и `medium` получают поддерживающий ответ без медицинской самоуверенности;
- `high` получает кризисный режим с ясным безопасным следующим шагом;
- `emergency` получает короткий emergency-протокол с обращением к локальным экстренным службам или доверенному человеку;
- несовершеннолетний не получает совет скрывать насилие, эксплуатацию, самоповреждение, угрозы или опасность;
- unsafe response исправляется или блокируется safety checker.

## Release decision

Релиз v0.1 можно считать готовым, когда:

- все P0 закрыты;
- `make check` проходит;
- QA, Safety Reviewer и Product/Clinical Reviewer не имеют блокирующих замечаний;
- известные ограничения записаны;
- документация не противоречит фактическому поведению;
- нет открытых P0-дефектов.

Если эти условия не выполнены, статус должен оставаться: "RC не готов к выпуску, требуется доработка".
